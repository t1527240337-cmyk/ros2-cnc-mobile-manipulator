# 关键工程问题、根因与解决方法

本文按“现象—错误假设—根因—通用修复—验证”记录关键工程问题，确保修改具有
可解释的因果依据，而不是依赖不可复现的参数试错。

## 1. 工件在夹爪未接触时飞起

- 现象：工件在夹爪靠近后直接跟随末端，甚至斜着悬空。
- 错误假设：MoveIt 的 AttachedCollisionObject 等于物理抓取。
- 根因：早期实现用仿真附着或实体位姿更新表达业务状态，绕过接触、摩擦和重力。
- 修复：运输阶段不使用 DetachableJoint，不写 entity pose。双指分别产生同一实体的
  新触觉接触后进入有限力保持，再执行 30 mm 无辅助试举；相对位姿和倾角通过后才把
  AttachedCollisionObject 加入 MoveIt，它只服务碰撞规划。
- 验证：关闭抓取条件任意一项都会失败；未被选择的工件不能移动。

## 2. 位置控制夹爪夹不住高速运动工件

- 现象：增加摩擦仍会滑落，继续增加摩擦又导致数值不稳定。
- 根因：纯位置目标会持续追求完全闭合，接触后可能产生很大的数值刚度；另一方面，
  只减速或只调摩擦不能形成可测量的载荷保持。
- 修复：位置模式用于搜索接触，双指接触后读取关节位置并转为有界保持目标和最大力；
  指垫使用 V 形接触面提高几何包络，摩擦和控制力同时处于可解释范围。
- 验证：记录左右指关节、双侧接触、总闭合量、试举和运输期间保持状态。

## 3. Nav2 到达后底盘反复前后摆动

- 现象：全局导航已经成功，AprilTag 对位仍长时间转圈或来回修正。
- 根因之一：把同一张延迟的 Tag TF 在控制循环中重复积分，旧测量继续驱动机器人，
  新帧到达时误差反向，于是形成极限环；稳定计数也可能错误地重复计算同一帧。
- 修复：Tag stamp 只在新图像到达时更新控制。上一命令最多维持一个 5 Hz 相机周期，
  超过 0.30 s 立即停底盘；三次稳定必须来自三张独立图像。
- 验证：回归曾经在 75 s 内振荡超时的 machine_3 种子，并统计对位耗时和最终误差。

## 4. 放置接触已经发生却报告“接触丢失”

- 现象：日志先显示支撑碰撞，约 7 s 后 MoveIt 取消完成，随后报
  `lost fresh support contact`。
- 根因：接触事件触发了轨迹提前停止，但取消动作耗时超过 1 s 的事件新鲜度窗口；
  停机验证又检查同一个瞬时事件，形成时序竞争。
- 修复：事件触发负责证明“为什么停止”；取消完成后验证当前 TCP 位于安全放置包络且
  抓持仍有效；开爪前再次要求当前支撑接触。历史事件不能直接授权释放。
- 验证：取消耗时长于接触窗口时仍可继续，但移除当前支撑后绝不能开爪。

## 5. 只靠触觉决定是否开始夹取

- 现象：看起来像“触觉成功后才夹”，逻辑顺序不自然。
- 根因：混淆了闭合动作和成功提交。触觉不是开始闭合的前置条件，而是闭合过程中识别
  接管对象和切换保持控制的反馈。
- 修复顺序：视觉目标与 IK 筛选 → 张开夹爪 → 运动到预抓取 → 直线接近 →
  启动闭合 → 双指触觉识别实体 → 有界力保持 → 试举验证 → 提交 PICK。
- 验证：无触觉时夹爪仍会执行搜索闭合，但到达闭合极限后必须失败，不能创建持有状态。

## 6. WSL 墙钟时间很长

- 现象：一次任务墙钟数百秒，误以为现实机器人也需要同样时间。
- 根因：WSL 的 Gazebo 渲染、物理和 ROS 进程争用 CPU，real-time factor 可低至
  0.3–0.4。墙钟时间不等于仿真时钟，更不等于实机节拍。
- 修复：分别记录 wall time、simulation time、RTF 和各 BT 叶节点耗时；云端使用
  原生 Ubuntu 多核 CPU，GPU 仅承担离屏渲染和编码。速度优化以仿真时钟和路径合理性
  为准，不通过放宽证据条件“加速”。
- 验证：同一 seed 在本机和云端比较仿真时间、墙钟和 RTF。

## 7. ROS setup 在 set -u 下报未绑定变量

- 现象：`AMENT_TRACE_SETUP_FILES: unbound variable`。
- 根因：脚本先启用 `set -u`，而 ROS 生成的 setup 脚本读取可选的未定义环境变量。
- 修复：source ROS setup 前局部 `set +u`，source 后恢复 `set -u`；公共脚本统一
  通过 `setup_ros_env.sh` 初始化，调用者不各自复制环境逻辑。
- 验证：全新非交互 shell、tmux 和 Docker 中分别构建。

## 8. LLM 把电池状态数字 2 解释成充电

- 现象：ROS 快照中的 `power_supply_status=2` 被模型误读。
- 根因：把 ROS 枚举裸整数直接交给语言模型，语义依赖外部消息定义。
- 修复：保留原始整数供审计，同时加入 `power_supply_status_name=DISCHARGING` 和
  `state_name=PROCESSING`；未知值明确输出 `UNRECOGNIZED_<n>`，不猜测。
- 验证：单元测试覆盖已知与未知枚举，并用真实模型做只读状态查询。

## 9. 端点 IK 可达不等于接近走廊可执行

- 现象：seed 124 的预抓取位和最终夹取位均通过碰撞感知 IK，但直线和 PTP 两条执行路径都
  超时。控制器记录显示五个关节到位，`arm_wrist_1_joint` 在距目标约 0.261 rad 处受阻。
- 根因：早期原料抓取从侧面横向进入；无固定槽位场景中，目标旁边可能存在另一件原料。
  单独检查目标端点 IK 并不能证明从当前位姿到端点的整条扫掠体无碰撞。录像和场景布局
  证明横向预抓取走廊穿过邻近工件，而不是超时不足或工作空间边缘。
- 通用处理：把同类直立圆柱的抓取改为目标正上方预抓取后垂直下探，使接近走廊只占用
  目标自身上方空间；同时依据实际 Tag—料台刚性偏移校正 Planning Scene。规划和执行
  仍需成功，不能通过放宽到达阈值或移动特定 seed 的工件解决。
- 验证：正式 30-seed 保留原始 29/30；修复后 seed 124 从全新场景完整通过。定向复测
  不回填原统计，完整口径见 `evaluation_results.md`。

## 10. 无界面录像文件存在但没有图像帧

- 现象：Gazebo 物理流程正常，录像节点启动后 MP4 始终为零帧。
- 根因：固定观察相机在正式评测世界中按需关闭；普通 topic bridge 不会自动激活
  `gz-sim` 的 image 传输，而且录像订阅的 QoS 与 image bridge 不匹配。
- 通用处理：正式世界保持相机关闭，录像脚本原子生成仅把观察相机设为
  `always_on` 的派生世界；使用 `ros_gz_image image_bridge`，录像节点采用与其
  匹配的可靠 QoS。提交订单前先验证 partial MP4 已有帧，失败则不运行演示。
- 验证：原始 720p 录像 151.70 s，NVENC 生成 75.85 s 主片和 83.85 s 交付版；
  普通 30-seed 评测仍不承担观察相机渲染成本。

## 11. Agent 在一次用户请求中连续执行两个状态变更

- 现象：模型先成功 `submit_order`，下一轮又调用 `start_automatic`，虽都属于白名单，
  但同一请求产生了两个业务写操作。
- 根因：主机只校验“单次模型回复最多一个写工具”，没有跨工具循环累计状态；提示词不是
  权限边界，模型在后续轮次仍能看到所有写工具。
- 通用处理：第一个写工具执行后，主机动态从后续 Schema 中移除全部状态变更工具，仅暴露
  查询工具；累计写次数校验作为第二道防线。被底层拒绝的写请求也消耗预算，以应对结果不确定。
- 验证：新增跨轮次能力收缩与 fail-closed 测试；真实 DeepSeek 演示只执行一次
  `submit_order`，之后只能 `get_task_status` 或回复。

## 故障分析原则

先说明可观测证据，再说明状态提交点；先找跨种子、跨工位都成立的因果根因，再决定修改。
不能为了让特定 seed 通过而直接放宽阈值。阈值必须来自传感器频率、机械间隙、
工作空间、安全包络或统计分布，并由独立测试验证。
