我们先把 [test_domain.py](/home/taoxu/Embodied_Robotic_Arm/src/factory_core/test/test_domain.py) 定位清楚：

它不是实现生产功能的代码，而是“检查生产功能是否符合设计”的代码。你可以把它理解为一份可自动执行的需求说明书。

如果某次修改破坏了“加工时不能开门”“低电量先充电”等规则，这些测试就会立刻失败。

## 一、设计目的

这个文件测试两个层次。

### 1. `MachineTests`：测试单台机床

它只关心一台机床自身的状态转换，例如：

```
IDLE
  → 开门
  → 装入零件
READY
  → 关门
  → 启动加工
PROCESSING
  → 加工时间结束
DONE
  → 卸下零件
IDLE
```

它还检查安全互锁：

```
PROCESSING 状态下禁止开门
```

### 2. `MissionTests`：测试整个生产任务

它关注多个对象协作：

- 工厂里有三台机床。
- 订单要求加工若干零件。
- 调度器决定下一步做什么。
- 仿真引擎执行调度决定。
- 低电量时需要充电。
- 故障机床中有零件时需要阻塞任务。
- 当前状态可以保存和恢复。

所以它测试的不是单个函数，而是一个小型“语义生产闭环”。

# 二、输入输出

这个测试文件没有键盘输入，也不直接操作 ROS、Gazebo 或真实机器人。

每个测试的输入都是在代码中构造的对象，例如：

```
machine = Machine("machine_1", cycle_seconds=2.0)
```

这里创建了一台机床：

- `machine_id` 是 `"machine_1"`
- 一个加工周期为 `2.0` 秒
- 其他字段使用默认值

初始状态大致是：

```
mode = MachineMode.IDLE
door_open = False
part_id = ""
remaining_seconds = 0.0
```

测试的输出不是普通函数的返回值，而是测试结果：

```
ok       表示测试通过
FAIL     表示断言不成立
ERROR    表示执行过程中出现了意外异常
```

例如：

```
self.assertEqual(machine.mode, MachineMode.DONE)
```

含义是：

> 我预期机床现在是 `DONE`。如果实际不是，测试失败。

## 3. 正常加工周期测试

```py
def test_valid_cycle(self):
    machine = Machine("machine_1", cycle_seconds=2.0)
```

这是测试的“准备阶段”，先创建机床。

```
machine.open_door()
machine.load("raw_001")
machine.close_door()
machine.start()
```

依次模拟：

1. 打开机床门。
2. 装入编号为 `raw_001` 的毛坯。
3. 关闭机床门。
4. 启动加工。

状态变化是：

```
创建机床：IDLE，门关闭，无零件
open_door：IDLE，门打开
load：READY，门打开，内部有 raw_001
close_door：READY，门关闭
start：PROCESSING，剩余加工时间为 2 秒
```

接下来：

```
machine.tick(2.0)
```

`tick()` 表示让领域时间向前推进。

它不是让程序真的等待两秒，而是立即计算：

```
remaining_seconds = 2.0 - 2.0
```

剩余时间变为零，所以机床进入：

```
MachineMode.DONE
```

然后验证：

```
self.assertEqual(machine.mode, MachineMode.DONE)
```

如果 `tick(2.0)` 后机床仍然是 `PROCESSING`，这里就会失败。

最后卸料：

```
machine.open_door()
self.assertEqual(machine.unload(), "raw_001")
```

`unload()` 应该返回机床内部零件的编号。

这里验证了两个事实：

- 加工完成后允许卸料。
- 卸下来的仍然是原来的 `raw_001`，零件没有凭空被替换。

注意：当前 `Machine.tick()` 在加工完成时已经把门设置为打开，所以这里再次调用 `open_door()` 不会改变结果。可以把它理解为明确表达“卸料前确保门已经打开”。

## 4. 加工时禁止开门

```
def test_door_cannot_open_during_processing(self):
```

前半段和正常加工一样：

```
machine = Machine("machine_1")
machine.open_door()
machine.load("raw_001")
machine.close_door()
machine.start()
```

执行完以后，机床处于：

```
mode = PROCESSING
door_open = False
part_id = raw_001
```

关键代码是：

```
with self.assertRaises(ValueError):
    machine.open_door()
```

它的含义不是“忽略异常”，而是：

> 接下来的代码必须抛出 `ValueError`，否则测试失败。

因此可能有三种结果：

```
抛出 ValueError       测试通过
没有抛出异常           测试失败
抛出其他类型的异常      测试报错
```

这条测试把一个非常重要的安全规则固化下来了：

```
PROCESSING → open_door 是非法转换
```

以后即使有人修改 `Machine.open_door()`，也不能悄悄移除这条互锁。

## 5. 三零件订单完成测试

```
state = FactoryState.default(cycle_seconds=5.0)
```

它创建默认工厂状态，内部包含三台机床：

```
{
    "machine_1": Machine(...),
    "machine_2": Machine(...),
    "machine_3": Machine(...),
}
```

默认有三个与 Gazebo 实体一一对应的毛坯：

```
raw_part_count = 3
```

然后创建订单：

```
order = ProductionOrder("order-1", 3, list(state.machines))
```

三个位置参数分别是：

```
"order-1"             订单编号
3                     要加工三个零件
list(state.machines)  允许使用的机床编号
```

这里容易困惑：

```
list(state.machines)
```

`state.machines` 是字典。直接把字典传给 `list()`，得到的是字典的键：

```
["machine_1", "machine_2", "machine_3"]
```

不是三个 `Machine` 对象。

接下来：

```
result = SimulationEngine(state, order).run()
```

这里连续做了两件事：

```
engine = SimulationEngine(state, order)
result = engine.run()
```

`run()` 内部重复执行：

```
decision = scheduler.next_decision(state, order)
engine.step()
```

大致流程是：

```
拿一个毛坯
→ 装入 machine_1
→ 拿第二个毛坯
→ 装入 machine_2
→ 拿第三个毛坯
→ 装入 machine_3
→ 等待加工
→ 从完成的机床取出成品
→ 放入成品框
→ 重复直到三个零件完成
```

最终验证四件事：

```
self.assertEqual(result.kind, DecisionKind.COMPLETE)
```

调度器最后返回“订单完成”，而不是阻塞或超出步数。

```
self.assertEqual(order.completed, 3)
```

订单对象记录完成了三个零件。

```
self.assertEqual(state.finished_part_count, 3)
```

成品框中有三个成品。

```
self.assertEqual(state.raw_part_count, 0)
```

初始三个毛坯全部完成，因此原料库存归零。

这几条断言从不同角度检查数据一致性。不能只检查 `order.completed`，因为订单计数可能增加了，但成品框数量可能忘记增加。

## 6. 低电量先充电

```
state = FactoryState.default()
state.battery = 0.20
```

电量使用 `0.0～1.0` 表示：

```
0.20 = 20%
0.80 = 80%
1.00 = 100%
```

默认调度器的低电量阈值是：

```
low_battery = 0.25
```

因此 20% 已经低于 25%。

执行一步：

```
self.assertEqual(engine.step().kind, DecisionKind.DOCK)
```

此时机器人手里没有零件，所以调度器应该选择回充电站，而不是先拿新毛坯。

`engine.step()` 不只是返回决定，还会应用这个决定。因此它会模拟充电，把电量充到目标值。

然后验证：

```
self.assertGreaterEqual(
    state.battery,
    Scheduler().charge_target,
)
```

默认目标电量是 80%。

这里使用 `assertGreaterEqual`，表示：

```
实际电量 >= 目标电量
```

而不是要求浮点数必须完全相等。浮点数经过计算后可能出现很小的精度误差，因此范围判断通常更稳妥。

## 7. 手里有零件时先安全放置

```
self.assertEqual(engine.step().kind, DecisionKind.PICK_RAW)
```

第一次执行后，机器人已经拿起一个毛坯。

此时关键状态是：

```
state.held_part_id = "raw_001"
state.held_part_kind = HeldPartKind.RAW
state.pending_machine_id = "machine_1"
```

然后人为模拟电量突然下降：

```
state.battery = 0.10
```

虽然电量只有 10%，但是机器人手里有零件。如果此时直接回充电站，就意味着它带着零件离开当前安全转运流程。

所以第二步必须是：

```
DecisionKind.LOAD_MACHINE
```

而不是：

```
DecisionKind.DOCK
```

这对应调度器中的优先级：

```
手里有毛坯
    优先装入已经选定的机床
然后
    再处理低电量充电
```

这是项目的重要不变量：

> 低电量不能破坏零件归属，必须先完成安全放置。

## 8. 故障机床困住零件

```
order = ProductionOrder("order-4", 1, ["machine_1"])
```

这个订单只允许使用 `machine_1`。

前两步：

```
engine.step()
engine.step()
```

分别是：

```
第一步：PICK_RAW
第二步：LOAD_MACHINE
```

第二步完成后：

```
machine_1 正在加工
machine_1 内有 raw_001
机器人手里没有零件
```

然后注入故障：

```
state.machines["machine_1"].inject_fault(7)
```

`7` 是模拟的故障码。

注入后：

```
mode = FAULT
fault_code = 7
part_id = raw_001
```

注意，故障不会让零件凭空消失。零件仍然在机床里。

继续运行：

```
result = engine.run()
```

调度器发现：

- 允许使用的唯一机床发生故障。
- 故障机床内部还有零件。
- 不能自动开门取出。
- 也不能假装订单完成。

因此返回：

```
DecisionKind.BLOCKED
```

测试同时检查故障说明：

```
self.assertIn("manual intervention", result.detail)
```

`assertIn(a, b)` 的意思是验证 `a` 是否包含在 `b` 中。

这里要求错误说明中包含：

```
manual intervention
```

也就是需要人工干预。

这个测试保护了“零件唯一归属”原则：发生故障时，不能为了让流程继续而直接把零件传送回料框。

## 9. 检查点保存与恢复

```
engine.step()
```

执行一步后，机器人已经拿起毛坯。因此状态中存在有价值的中间数据：

```
held_part_id = "raw_001"
```

然后创建临时目录：

```
with tempfile.TemporaryDirectory() as directory:
```

进入 `with` 时创建目录；离开 `with` 时自动删除目录及其中的文件。

构造检查点路径：

```
store = CheckpointStore(
    Path(directory) / "checkpoint.json"
)
```

保存：

```
store.save(state, order)
```

它会把 `FactoryState` 和 `ProductionOrder` 转成 JSON。

恢复：

```
loaded_state, loaded_order = store.load()
```

这里叫“解包”：

```
返回值 = (恢复后的工厂状态, 恢复后的订单)

loaded_state = 第一个值
loaded_order = 第二个值
```

离开 `with` 后，临时 JSON 文件被删除，但已经加载到内存中的对象仍然存在。

最后验证：

```
self.assertEqual(
    loaded_state.held_part_id,
    state.held_part_id,
)
```

确保恢复后，系统仍然记得机器人手里拿着哪个零件。

```
self.assertEqual(
    loaded_order.order_id,
    order.order_id,
)
```

确保恢复的是同一个订单。

这里测试的是一次“往返”：

```
Python 对象
→ JSON 文件
→ 新的 Python 对象
```

所以叫 `round trip`。

# 四、关键状态

理解这个文件时，需要重点盯住四组状态。

## 1. `Machine.mode`

```
IDLE        空闲，可以准备上料
READY       已经有零件，等待启动
PROCESSING  正在加工
DONE        加工完成，可以下料
FAULT       故障
HELD        受控暂停
```

测试时不要只看调用了什么函数，要一直问：

> 这一行执行前是什么状态，执行后应该是什么状态？

## 2. 零件在哪里

主要字段是：

```
machine.part_id
state.held_part_id
state.raw_part_count
state.finished_part_count
```

一个零件只能在以下位置之一：

```
毛坯框
机器人夹爪
某台机床
成品框
```

不能同时出现在两个地方，也不能凭空消失。

## 3. 订单进度

```
order.started
order.completed
order.quantity
```

例如三零件订单最终应该满足：

```
started == 3
completed == 3
quantity == 3
```

`started` 表示已经送入机床开始加工的数量；`completed` 表示已经放入成品框的数量。两者不是一回事。

## 4. 调度结果

`DecisionKind` 表示下一步的高层语义动作：

```
PICK_RAW        拿毛坯
LOAD_MACHINE    把毛坯装入机床
PICK_FINISHED   从机床取成品
PLACE_FINISHED  把成品放入成品框
DOCK            回充电站
WAIT            等待加工
COMPLETE        订单完成
BLOCKED         无法继续
```

这里没有关节角度、速度或 `/cmd_vel`，因为领域调度器只决定“做什么”，不决定电机“怎么动”。

你的理解大部分已经对了。核心是：`Machine` 的构造函数不是“自动匹配类变量”，而是由 `@dataclass` 根据字段定义生成的。

# 一、设计目的

这里组合使用了三个 Python 机制：

- `@dataclass`：根据字段自动生成构造函数等样板代码。
- `@classmethod`：定义属于“类”的方法，常用于创建对象。
- `Decision + Scheduler + SimulationEngine`：把“决定下一步”和“执行下一步”分开。

它们组合后的关系是：

```python
FactoryState.default()
        ↓ 创建默认工厂

Scheduler.next_decision()
        ↓ 只判断下一步做什么

SimulationEngine.step()
        ↓ 执行这一步并修改状态

SimulationEngine.run()
        ↓ 重复 step，直到 COMPLETE 或 BLOCKED
```

# 二、输入输出

## 1. 为什么没看到 `Machine.__init__()`？

因为 `Machine` 使用了：

```py
@dataclass
class Machine:
    machine_id: str
    mode: MachineMode = MachineMode.IDLE
    door_open: bool = False
    part_id: str = ""
    remaining_seconds: float = 0.0
    cycle_seconds: float = 12.0
    fault_code: int = 0
```

`@dataclass` 会根据这些字段，近似生成：

```python
class Machine:
    def __init__(
        self,
        machine_id: str,
        mode: MachineMode = MachineMode.IDLE,
        door_open: bool = False,
        part_id: str = "",
        remaining_seconds: float = 0.0,
        cycle_seconds: float = 12.0,
        fault_code: int = 0,
    ):
        self.machine_id = machine_id
        self.mode = mode
        self.door_open = door_open
        self.part_id = part_id
        self.remaining_seconds = remaining_seconds
        self.cycle_seconds = cycle_seconds
        self.fault_code = fault_code
```

所以：

```python
Machine(
    f"machine_{index}",
    cycle_seconds=cycle_seconds,
)
```

等价于：

```python
Machine(
    machine_id=f"machine_{index}",
    cycle_seconds=cycle_seconds,
)
```

你的理解是对的：第一个位置参数对应第一个字段 `machine_id`。

但不是因为“没有父类就自动匹配”，而是因为 `@dataclass` 生成了构造函数。

------

## 2. 普通类不写 `__init__()` 会怎样？

例如：

```
class Student:
    name: str
```

可以创建：

```
student = Student()
```

这是因为它继承了最基础的 `object.__init__()`，但这个构造函数不接收你的业务参数。

下面会报错：

```
student = Student("小明")
```

而且字段注解：

```
name: str
```

只是告诉编辑器“这里应该是字符串”，不会自动执行：

```
self.name = name
```

因此下面也会报错：

```
student = Student()
print(student.name)
```

因为这个实例还没有真正获得 `name` 属性。

只有加上 `@dataclass`：

```
@dataclass
class Student:
    name: str
```

它才会自动生成能接收 `name` 的构造函数。

------

## 3. 如果自己写了 `__init__()`，默认生成的还能用吗？

如果在 `@dataclass` 类中自己定义 `__init__()`，dataclass 就不会再为你生成那个默认构造函数。

例如：

```python
@dataclass
class Student:
    name: str
    age: int = 18

    def __init__(self, name: str):
        self.name = name
```

这时：

```
Student("小明")
```

可以使用，但 `age` 的初始化需要你自己负责。

如果只是想在自动初始化之后做检查，通常不要重写 `__init__()`，而是使用：

```python
@dataclass
class Student:
    name: str
    age: int

    def __post_init__(self):
        if self.age < 0:
            raise ValueError("年龄不能为负数")
```

执行顺序是：

```
dataclass 自动生成的 __init__
              ↓
完成字段赋值
              ↓
自动调用 __post_init__
```

这样既保留自动构造函数，又能添加校验逻辑。

# 三、执行流程

## 1. `@dataclass` 到底是什么？

`@` 表示装饰器。

下面的写法：

```python
@dataclass
class Machine:
    ...
```

可以粗略理解为：

```python
class Machine:
    ...

Machine = dataclass(Machine)
```

`dataclass()` 接收原来的类，检查字段注解，然后补充常用方法，主要包括：

```
__init__()   创建对象
__repr__()   打印对象
__eq__()     比较两个对象
```

所以可以直接打印：

```python
machine = Machine("machine_1")
print(machine)
```

大致得到：

```python
Machine(
    machine_id='machine_1',
    mode=<MachineMode.IDLE: 0>,
    door_open=False,
    ...
)
```

------

## 2. `@classmethod` 是什么？

普通实例方法的第一个参数是 `self`：

```python
def open_door(self):
    self.door_open = True
```

调用：

```python
machine.open_door()
```

Python 会自动把 `machine` 传给 `self`。

类方法的第一个参数是 `cls`：

```python
@classmethod
def default(cls, cycle_seconds: float = 12.0):
    ...
```

调用：

```
FactoryState.default()
```

Python 会自动把 `FactoryState` 类传给 `cls`。

可以近似理解为：

```python
FactoryState.default(
    cls=FactoryState,
)
```

但实际上调用时不需要、也不能手动写这个 `cls=`。

所以：

```python
return cls(machines=machines)
```

此时基本等价于：

```python
return FactoryState(machines=machines)
```

### 为什么不直接写 `FactoryState(...)`？

**使用 `cls` 可以兼容子类**。

假设以后有：

```python
class RealFactoryState(FactoryState):
    pass
```

调用：

```
RealFactoryState.default()
```

此时：

```
cls
```

就是：

```
RealFactoryState
```

所以它会创建子类对象，而不是固定创建 `FactoryState`。

因此：

- `self` 代表当前对象。
- `cls` 代表当前类。
- `self` 常用于操作已经存在的对象。
- `cls` 常用于创建对象或访问类级别信息。

------

## 3. `FactoryState.default()` 怎样创建三台机床？

完整代码是：

```py
@classmethod
def default(
    cls,
    cycle_seconds: float = 12.0,
) -> "FactoryState":
    machines = {
        f"machine_{index}": Machine(
            f"machine_{index}",
            cycle_seconds=cycle_seconds,
        )
        for index in range(1, 4)
    }
    return cls(machines=machines)
```

其中：

```
range(1, 4)
```

产生：

```
1、2、3
```

字典推导式等价于：

```py
machines = {}

for index in range(1, 4):
    machine_id = f"machine_{index}"

    machines[machine_id] = Machine(
        machine_id,
        cycle_seconds=cycle_seconds,
    )
```

最终结果是：

```py
machines = {
    "machine_1": Machine("machine_1"),
    "machine_2": Machine("machine_2"),
    "machine_3": Machine("machine_3"),
}
```

然后：

```py
return cls(machines=machines)
```

把这个字典传给 `FactoryState` 构造函数。

其他字段没有传，所以使用默认值：

```py
raw_part_count: int = 3
finished_part_count: int = 0
battery: float = 1.0
held_part_id: str = ""
held_part_kind: HeldPartKind = HeldPartKind.NONE
pending_machine_id: str = ""
charging: bool = False
simulated_time: float = 0.0
next_part_serial: int = 1
events: list[str] = field(default_factory=list)
```

------

## 4. `f"..."` 是什么？

这是 Python 的格式化字符串，叫 f-string。

例如：

```py
index = 2
machine_id = f"machine_{index}"
```

得到：

```
"machine_2"
```

`{}` 中可以放变量或表达式：

```py
quantity = 3

print(f"订单数量是 {quantity}")
print(f"下一个数量是 {quantity + 1}")
```

结果：

```
订单数量是 3
下一个数量是 4
```

项目中还有：

```py
f"raw_{state.next_part_serial:03d}"
```

其中：

```
:03d
```

表示：

- `d`：按十进制整数显示。
- `3`：总宽度至少三位。
- `0`：不够三位时前面补零。

因此：

```
1   → raw_001
2   → raw_002
12  → raw_012
123 → raw_123
```

------

## 5. `run(max_steps=500)` 的理解是对的

```py
def run(self, max_steps: int = 500) -> Decision:
```

调用：

```
engine.run()
```

等价于：

```py
engine.run(max_steps=500)
```

也可以自己指定：

```
engine.run(max_steps=100)
```

这里限制最大执行步数，是为了防止错误逻辑造成无限循环。

主体：

```py
for _ in range(max_steps):
    decision = self.step()

    if decision.kind in (
        DecisionKind.COMPLETE,
        DecisionKind.BLOCKED,
    ):
        return decision
```

`_` 表示这个循环变量不需要使用。

它最多重复执行 500 次：

```
step 1
step 2
step 3
...
step 500
```

如果 500 步还没有完成：

```py
return Decision(
    DecisionKind.BLOCKED,
    detail="step budget exhausted",
)
```

------

## 6. `next_decision()` 做了什么？

```py
decision = self.scheduler.next_decision(
    self.state,
    self.order,
)
```

它读取工厂状态和订单状态，判断下一步应该做什么。

重要的是：

> `next_decision()` 只作决定，不修改状态。

例如当前情况不同，它可能返回：

```
Decision(DecisionKind.PICK_RAW, "machine_1")
```

或者：

```
Decision(DecisionKind.DOCK)
```

或者：

```
Decision(DecisionKind.COMPLETE)
```

真正修改状态的是后面的 `SimulationEngine.step()`。

两者职责是：

```
Scheduler.next_decision()
    回答：下一步做什么？

SimulationEngine.step()
    回答：执行这一步后，状态怎样变化？
```

------

## 7. 订单完成后，确实是下一次调度返回 `COMPLETE`

你的理解完全正确。

假设订单要求一个零件：

```
order.quantity = 1
```

执行放置成品这一步：

```py
elif decision.kind == DecisionKind.PLACE_FINISHED:
    state.finished_part_count += 1
    self.order.completed += 1
```

执行后：

```
order.completed == 1
order.quantity == 1
```

但是这一轮 `step()` 返回的仍然是：

```py
DecisionKind.PLACE_FINISHED
```

因此 `run()` 暂时不会退出。

下一轮再次执行：

```
decision = self.step()
```

`next_decision()` 首先检查：

```py
if order.completed >= order.quantity:
    return Decision(
        DecisionKind.COMPLETE,
        detail="requested quantity completed",
    )
```

这次返回 `COMPLETE`，于是：

```py
if decision.kind in (
    DecisionKind.COMPLETE,
    DecisionKind.BLOCKED,
):
    return decision
```

`run()` 正式结束。

流程是：

```
PLACE_FINISHED
    ↓ completed 加一
下一次 step
    ↓
next_decision 发现数量完成
    ↓
返回 COMPLETE
    ↓
run 退出循环
```

# 四、关键状态

## 1. 为什么 `Decision.machine_id` 默认是空字符串？

`Decision` 定义是：

```py
@dataclass(frozen=True)
class Decision:
    kind: DecisionKind
    machine_id: str = ""
    detail: str = ""
```

只有 `kind` 是必传参数。

下面：

```py
Decision(
    DecisionKind.COMPLETE,
    detail="requested quantity completed",
)
```

等价于：

```py
Decision(
    kind=DecisionKind.COMPLETE,
    machine_id="",
    detail="requested quantity completed",
)
```

这里 `machine_id=""` 没有问题，因为“订单完成”不是针对某一台机床的动作。

不同决定对 `machine_id` 的需求不同：

| 决定             | 是否需要机床编号           |
| ---------------- | -------------------------- |
| `PICK_RAW`       | 需要，表示准备送去哪台机床 |
| `LOAD_MACHINE`   | 需要，表示装入哪台机床     |
| `PICK_FINISHED`  | 需要，表示从哪台机床取     |
| `PLACE_FINISHED` | 不需要                     |
| `DOCK`           | 不需要                     |
| `WAIT`           | 不需要                     |
| `COMPLETE`       | 不需要                     |
| `BLOCKED`        | 有时需要                   |

例如：

```py
return Decision(
    DecisionKind.PICK_RAW,
    idle[0].machine_id,
    "fill idle machine before collecting output",
)
```

三个位置参数依次对应：

```
kind
machine_id
detail
```

而完成订单时：

```py
Decision(
    DecisionKind.COMPLETE,
    detail="requested quantity completed",
)
```

特意跳过了 `machine_id`，所以使用默认空字符串。

`step()` 只有处理需要机床的决定时才读取：

```
state.machines[decision.machine_id]
```

处理 `COMPLETE` 时不会读取它。

------

## 2. `held_part_id`

```
held_part_id: str = ""
```

表示机器人夹爪当前拿着的零件编号。

例如：

```
""              夹爪为空
"raw_001"       拿着一号毛坯
"finished_001"  拿着一号成品
```

执行拿毛坯：

```
state.held_part_id = "raw_001"
```

执行装载：

```
machine.load(state.held_part_id)
state.held_part_id = ""
```

也就是零件从夹爪转移到了机床。

------

## 3. `held_part_kind`

```
held_part_kind: HeldPartKind = HeldPartKind.NONE
```

它表示夹爪中零件的种类：

```
class HeldPartKind(IntEnum):
    NONE = 0
    RAW = 1
    FINISHED = 2
```

对应关系是：

| 值         | 含义     |
| ---------- | -------- |
| `NONE`     | 没拿零件 |
| `RAW`      | 拿着毛坯 |
| `FINISHED` | 拿着成品 |

为什么有了 `held_part_id`，还需要 `held_part_kind`？

因为调度器不应该通过字符串名称猜测零件类型，例如不应该依赖：

```
held_part_id.startswith("raw_")
```

明确的枚举状态更可靠：

```py
if state.held_part_kind == HeldPartKind.RAW:
    return DecisionKind.LOAD_MACHINE

if state.held_part_kind == HeldPartKind.FINISHED:
    return DecisionKind.PLACE_FINISHED
```

------

## 4. `pending_machine_id`

```
pending_machine_id: str = ""
```

它表示：

> 机器人拿起这个毛坯后，计划把它送到哪台机床。

拿毛坯时：

```
state.pending_machine_id = decision.machine_id
```

例如：

```
held_part_id = raw_001
held_part_kind = RAW
pending_machine_id = machine_2
```

含义是：

```
夹爪拿着 raw_001
这个毛坯已经分配给 machine_2
下一步必须装入 machine_2
```

下一次调度：

```py
if state.held_part_kind == HeldPartKind.RAW:
    return Decision(
        DecisionKind.LOAD_MACHINE,
        state.pending_machine_id,
    )
```

装载完成后清空：

```
state.held_part_id = ""
state.held_part_kind = HeldPartKind.NONE
state.pending_machine_id = ""
```

它的作用是让“拿毛坯”和“装机床”这两个分开的步骤仍然保持关联。

------

## 5. `next_part_serial`

```
next_part_serial: int = 1
```

它是下一个毛坯的流水号。

第一次拿毛坯：

```
held_part_id = "raw_001"
next_part_serial = 2
```

第二次：

```
held_part_id = "raw_002"
next_part_serial = 3
```

代码是：

```py
state.held_part_id = (
    f"raw_{state.next_part_serial:03d}"
)

state.next_part_serial += 1
```

先使用编号，再把编号加一。

它可以保证零件编号不会重复。

------

## 6. `events` 和 `default_factory`

```
events: list[str] = field(default_factory=list)
```

`events` 是事件日志列表，例如：

```py
[
    "0000.00s picked raw_001 for machine_1",
    "0002.00s loaded raw_001 into machine_1; cycle started",
]
```

为什么不直接写：

```
events: list[str] = []
```

因为列表是可变对象。如果多个实例共享同一个默认列表，就可能出现：

```
工厂 A 添加了一条事件
工厂 B 的事件列表里也出现了
```

`default_factory=list` 的意思是：

> 每次创建 `FactoryState` 对象时，都重新调用一次 `list()`，生成一个全新的列表。

可以粗略理解为：

```
self.events = list()
```

因此：

```py
state_a = FactoryState.default()
state_b = FactoryState.default()

state_a.events.append("事件A")
```

此时：

```py
state_a.events == ["事件A"]
state_b.events == []
```

两个工厂对象不会共享日志。

**Python 和 C++/Java 很不一样的地方：Python 对象的成员通常保存的是“对象引用”，不是把另一个对象完整复制进来。因此两个独立对象完全可以共同引用同一个列表。**

### 1. 两个实例为什么可能共享同一个列表？

先看这个例子：

```python
shared_events = []

state_a = FactoryState.default()
state_b = FactoryState.default()

state_a.events = shared_events
state_b.events = shared_events
```

`state_a` 和 `state_b` 确实是两个不同对象：

```py
state_a is state_b
# False
```

但它们的 `events` 可以指向同一个列表：

```py
state_a.events is state_b.events
# True
```

内存关系类似：

```
state_a ──→ FactoryState对象A
               │
               └── events ──┐
                             ↓
                         同一个列表
                             ↑
state_b ──→ FactoryState对象B │
               │             │
               └── events ───┘
```

于是：

```py
state_a.events.append("机器启动")
```

查看另一个对象时：

```py
print(state_b.events)
```

也会看到：

```py
["机器启动"]
```

对象 A 和对象 B 是独立的，不代表它们引用的所有子对象也一定不同。

可以把它想象成：

> 两个人是独立的人，但两个人可以共同拿着同一本笔记本。一个人在笔记本上写字，另一个人看到的笔记本也会变化。

------

### 2. `events=[]` 为什么危险？

列表字面量：

```
[]
```

会创建一个列表对象。

如果这个列表被作为默认值保存下来，然后每次构造对象都把同一个默认列表赋给 `events`，不同实例就会共享它。

在现代 Python 中，dataclass 会直接阻止这种写法：

```py
@dataclass
class FactoryState:
    events: list[str] = []
```

通常会报错：

```
ValueError: mutable default ... is not allowed:
use default_factory
```

这正是 dataclass 在帮助开发者避免共享可变对象。

正确写法：

```py
events: list[str] = field(default_factory=list)
```

近似表示每次构造对象都执行：

```py
self.events = list()
```

所以：

```
创建 state_a → 调用一次 list() → 列表A
创建 state_b → 再调用一次 list() → 列表B
```

得到：

```py
state_a.events is state_b.events
# False
```

不可变类型通常没有这个问题：

```py
battery: float = 1.0
held_part_id: str = ""
```

因为数字和字符串不能被原地修改。执行：

```py
state_a.battery = 0.5
```

是让 `state_a.battery` 改为引用另一个数字，不会修改 `state_b.battery`。

## 7.from_dict 和 to_dict 作用

```py
@classmethod
def from_dict(cls, data: dict[str, Any]) -> "Machine":
    value = dict(data)
    value["mode"] = MachineMode(value["mode"])
    return cls(**value)
```

它的目的是：

> 把一个普通字典恢复成 `Machine` 对象。

### 输入

假设从 JSON 中读取到：

```json
data = {
    "machine_id": "machine_1",
    "mode": 2,
    "door_open": False,
    "part_id": "raw_001",
    "remaining_seconds": 8.0,
    "cycle_seconds": 12.0,
    "fault_code": 0,
}
```

它现在只是字典，不是 `Machine`：

```
type(data)
# dict
```

不能这样调用：

```
data.tick(1.0)
```

因为字典没有 `tick()` 方法。

### 第一步：复制字典

```
value = dict(data)
```

相当于：

```
value = data.copy()
```

为什么要复制？

因为后面需要修改：

```
value["mode"] = ...
```

如果直接修改 `data`，调用者传进来的原始字典也会被改变。

现在：

```
value is data
# False
```

但要注意，这是浅复制。对于这个函数已经足够，因为它只替换最外层的 `mode`。

### 第二步：恢复枚举

JSON 中保存的是：

```
"mode": 2
```

但领域对象需要的是：

```
MachineMode.PROCESSING
```

所以执行：

```
value["mode"] = MachineMode(value["mode"])
```

等价于：

```
value["mode"] = MachineMode(2)
```

结果是：

```
MachineMode.PROCESSING
```

转换后：

```
value = {
    "machine_id": "machine_1",
    "mode": MachineMode.PROCESSING,
    ...
}
```

### 第三步：`cls(**value)`

```
return cls(**value)
```

`**` 叫“**字典关键字参数解包**”。

例如：

```py
data = {
    "machine_id": "machine_1",
    "cycle_seconds": 5.0,
}
```

下面两个写法等价：

```py
Machine(**data)
Machine(
    machine_id="machine_1",
    cycle_seconds=5.0,
)
```

因此：

```
cls(**value)
```

当 `cls` 是 `Machine` 时，就近似等于：

```py
Machine(
    machine_id=value["machine_id"],
    mode=value["mode"],
    door_open=value["door_open"],
    part_id=value["part_id"],
    remaining_seconds=value["remaining_seconds"],
    cycle_seconds=value["cycle_seconds"],
    fault_code=value["fault_code"],
)
```

最终返回真正的 `Machine` 对象。

###  返回类型为什么写成字符串？

```py
-> "Machine"
```

它表示这个方法返回一个 `Machine` 对象。

之所以用引号，是因为解释到函数定义时，`Machine` 类本身还处于定义过程中。引号让 Python 暂时把它当作类型名称，而不是立即查找这个对象。

不过当前文件顶部已经有：

```
from __future__ import annotations
```

在现代 Python 中，有了它之后通常也可以写：

```
-> Machine
```

项目中的引号写法依然合法，也能明确表达“返回当前类对象”。



## `8.FactoryState.tick()` 做了什么？

```py
def tick(
    self,
    seconds: float,
    battery_drain: float = 0.001,
) -> None:
```

输入是：

- `seconds`：让仿真时间前进多少秒。
- `battery_drain`：每仿真秒消耗多少电量，默认是 `0.001`。
- 返回 `None`：不创建新状态，而是直接修改当前 `FactoryState`。

### 第一步：防止时间倒退

```
duration = max(0.0, seconds)
```

例如：

```
seconds = 3.0   → duration = 3.0
seconds = 0.0   → duration = 0.0
seconds = -2.0  → duration = 0.0
```

负时间被当作零，不能让加工进度倒退。

### 第二步：推进工厂总时间

```
self.simulated_time += duration
```

`+=` 不是重置，而是累加。

例如：

```
原来 simulated_time = 5.0
本次 duration = 2.0
新的 simulated_time = 7.0
```

`simulated_time` 表示整个工厂仿真从开始到现在经过了多少时间。

它不是某一台机床的加工时间，也不是因为三台机床加工相同产品才放在总体状态中。

正确关系是：

```
FactoryState.simulated_time
    整个工厂共享的时间轴

Machine.remaining_seconds
    每台机床各自剩余的加工时间
```

例如：

```
工厂当前时间：10秒

machine_1：还剩 3 秒
machine_2：还剩 8 秒
machine_3：没有加工
```

时间再前进两秒：

```
工厂当前时间：12秒

machine_1：还剩 1 秒
machine_2：还剩 6 秒
machine_3：仍然空闲
```

### 第三步：同时推进所有机床

```py
for machine in self.machines.values():
    machine.tick(duration)
```

`self.machines` 是：

```
{
    "machine_1": Machine(...),
    "machine_2": Machine(...),
    "machine_3": Machine(...),
}
```

`.values()` 取得所有 `Machine` 对象。

近似等于：

```py
machine_1.tick(duration)
machine_2.tick(duration)
machine_3.tick(duration)
```

为什么所有机床都要推进？

因为现实中时间是同时流逝的。当机器人花三秒装载 `machine_2` 时，已经处于加工状态的 `machine_1` 也同时加工了三秒。

不过 `Machine.tick()` 内部有判断：

```py
if self.mode != MachineMode.PROCESSING:
    return
```

所以只有正在加工的机床才会减少剩余时间。

### 第四步：计算电量变化率

```
rate = 0.03 if self.charging else -battery_drain
```

这是条件表达式，等价于：

```py
if self.charging:
    rate = 0.03
else:
    rate = -battery_drain
```

含义是：

```
正在充电：每秒增加 0.03，也就是 3%
没有充电：每秒减少 battery_drain
```

默认：

```
battery_drain = 0.001
```

也就是每秒消耗 0.1%。

### 第五步：更新电量并限制范围

```py
self.battery = min(
    1.0,
    max(
        0.0,
        self.battery + duration * rate,
    ),
)
```

先计算：

```
self.battery + duration * rate
```

例如当前电量为 50%，经过 10 秒，未充电：

```
0.5 + 10 * (-0.001)
= 0.49
```

然后：

```
max(0.0, 新电量)
```

保证不能低于 0%。

最后：

```
min(1.0, 新电量)
```

保证不能超过 100%。

因此电量始终满足：

```
0.0 <= battery <= 1.0
```

## 9. `add_event()` 做了什么？

```py
def add_event(self, message: str) -> None:
    self.events.append(
        f"{self.simulated_time:07.2f}s {message}"
    )
```

它给事件添加时间戳，然后放入日志列表。

格式：

```
:07.2f
```

含义是：

- `f`：浮点数。
- `.2`：保留两位小数。
- `7`：总宽度至少七位。
- `0`：前面不足时补零。

例如：

```
self.simulated_time = 12.3
message = "picked raw_001"
```

保存结果：

```
0012.30s picked raw_001
```

这样可以按时间观察整个任务：

```py
[
    "0000.00s picked raw_001 for machine_1",
    "0002.00s loaded raw_001 into machine_1; cycle started",
    "0005.00s picked raw_002 for machine_2",
]
```



## `10.FactoryState.to_dict()` 为什么需要？

```py
def to_dict(self) -> dict[str, Any]:
    value = asdict(self)
    value["machines"] = {
        key: asdict(machine) for key, machine in self.machines.items()
    }
    value["held_part_kind"] = int(self.held_part_kind)
    for machine in value["machines"].values():
        machine["mode"] = int(machine["mode"])
    return value

@classmethod
def from_dict(cls, data: dict[str, Any]) -> "FactoryState":
    value = dict(data)
    value["machines"] = {
        key: Machine.from_dict(machine)
        for key, machine in value["machines"].items()
    }
    value["held_part_kind"] = HeldPartKind(value["held_part_kind"])
    return cls(**value)
```

这部分代码主要解决两件事：

1. 安全地保存工厂中的可变状态，例如事件列表。
2. 在“Python 领域对象”和“可以写入 JSON 的普通字典”之间转换。

整体流程是：

```
FactoryState 对象
      ↓ to_dict()
普通字典
      ↓ json.dumps()
JSON 文件
      ↓ json.loads()
普通字典
      ↓ from_dict()
新的 FactoryState 对象
```

`tick()` 则负责让整个工厂的“仿真时间”统一向前推进。

`FactoryState` 中包含：

- 普通数字和字符串。
- `Machine` 对象。
- `HeldPartKind` 枚举。
- `MachineMode` 枚举。
- 多层字典和列表。

JSON 不理解“Python 的 `Machine` 对象是什么”，因此保存前需要转换成普通结构：

```
对象 → 字典
枚举 → 整数
嵌套 Machine → 嵌套字典
```

### 第一步：dataclass 转字典

```
value = asdict(self)
```

`asdict()` 来自：

```py
from dataclasses import asdict
```

它会递归读取 dataclass 字段。

例如：

```
state = FactoryState.default()
value = asdict(state)
```

得到类似：

```py
{
    "machines": {
        "machine_1": {
            "machine_id": "machine_1",
            "mode": MachineMode.IDLE,
            "door_open": False,
            ...
        },
        ...
    },
    "raw_part_count": 3,
    "finished_part_count": 0,
    "battery": 1.0,
    ...
}
```

结果已经是字典，但枚举值还需要显式转成整数。

### 第二步：转换所有机床

```py
value["machines"] = {
    key: asdict(machine)
    for key, machine in self.machines.items()
}
```

这是字典推导式。

展开后近似是：

```py
machine_values = {}

for key, machine in self.machines.items():
    machine_values[key] = asdict(machine)

value["machines"] = machine_values
```

结果：

```py
{
    "machine_1": {
        "machine_id": "machine_1",
        "mode": MachineMode.IDLE,
        ...
    },
    "machine_2": {...},
    "machine_3": {...},
}
```

**严格来说，前面的 `asdict(self)` 已经会递归转换 `Machine`，这里再次明确转换机床，主要是让嵌套机床结构清楚、可控。**

### 第三步：转换夹爪零件类型

```
value["held_part_kind"] = int(
    self.held_part_kind
)
```

例如：

```
HeldPartKind.NONE
```

转换为：

```
0
```

而：

```
HeldPartKind.RAW
```

转换为：

```
1
```

### 第四步：转换机床状态

```
for machine in value["machines"].values():
    machine["mode"] = int(machine["mode"])
```

例如：

```
MachineMode.PROCESSING
```

转换为：

```
2
```

转换后的结构适合写入 JSON：

```py
{
    "machines": {
        "machine_1": {
            "machine_id": "machine_1",
            "mode": 2,
            "door_open": False,
            ...
        }
    },
    "held_part_kind": 1,
    ...
}
```

##  `11.FactoryState.from_dict()` 怎样恢复？

```py
@classmethod
def from_dict(
    cls,
    data: dict[str, Any],
) -> "FactoryState":
```

它执行 `to_dict()` 的反向操作。

### 第一步：复制输入字典

```
value = dict(data)
```

避免直接修改调用者传入的顶层字典。

### 第二步：恢复所有 `Machine`

```py
value["machines"] = {
    key: Machine.from_dict(machine)
    for key, machine in value["machines"].items()
}
```

假设 JSON 读取后是：

```py
"machines": {
    "machine_1": {
        "machine_id": "machine_1",
        "mode": 2,
        ...
    }
}
```

循环执行：

```py
Machine.from_dict({
    "machine_id": "machine_1",
    "mode": 2,
    ...
})
```

得到：

```py
Machine(
    machine_id="machine_1",
    mode=MachineMode.PROCESSING,
    ...
)
```

所以最终 `machines` 恢复为：

```py
{
    "machine_1": Machine(...),
    "machine_2": Machine(...),
    "machine_3": Machine(...),
}
```

如果不执行这一步，`machines["machine_1"]` 就只是字典，后面无法调用：

```
machines["machine_1"].tick()
```

### 第三步：恢复 `HeldPartKind`

```py
value["held_part_kind"] = HeldPartKind(
    value["held_part_kind"]
)
```

例如：

```
1
```

恢复为：

```
HeldPartKind.RAW
```

### 第四步：创建 `FactoryState`

```
return cls(**value)
```

当 `cls` 是 `FactoryState` 时，近似等于：

```py
return FactoryState(
    machines=value["machines"],
    raw_part_count=value["raw_part_count"],
    finished_part_count=value["finished_part_count"],
    battery=value["battery"],
    held_part_id=value["held_part_id"],
    held_part_kind=value["held_part_kind"],
    pending_machine_id=value["pending_machine_id"],
    charging=value["charging"],
    simulated_time=value["simulated_time"],
    next_part_serial=value["next_part_serial"],
    events=value["events"],
)
```

至此，普通字典恢复成了有方法、有枚举状态的领域对象。

## 12.关键状态2

一定要区分这几个时间字段：

```
FactoryState.simulated_time
    整个工厂从仿真开始经过的总时间，只增加，不重置。

Machine.cycle_seconds
    一次完整加工需要的时间。

Machine.remaining_seconds
    当前这次加工还剩多少时间。
```

例如：

```
工厂总时间 simulated_time = 30 秒

machine_1:
    cycle_seconds = 12 秒
    remaining_seconds = 3 秒

machine_2:
    cycle_seconds = 12 秒
    remaining_seconds = 8 秒
```

因此，把 `simulated_time` 放在 `FactoryState` 中不是因为机床加工同一种产品，而是因为整个工厂需要一条统一时间轴。

可以用下面的代码验证“两个对象可以共享一个列表”：

```py
shared = []

class Example:
    pass

a = Example()
b = Example()

b.events = shared

print(a.events is b.events)

```

预期：

```
True
['event']
['event']
```

验证序列化往返：

```py
from factory_core.domain import FactoryState

state.add_event("factory created")

data = state.to_dict()
restored = FactoryState.from_dict(data)

print(type(data))
print(type(restored))
```

预期类型：

最关键的理解是：

```

from_dict：根据存储的数据，重新构造领域对象。
tick：让整个工厂的统一仿真时间前进，并同步更新机床和电量。
```
